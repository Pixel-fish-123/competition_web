## 第一部分 · 游戏核心规则（运行时）

### R1 基本盘面
- R1.1 7 层三角形地图，共 **27 格**：21 个任务格（id 0–20）+ 6 个能源格（id 21–26，第 7 层，**不可占领**）。
- R1.2 层级：L1=id 0（1 格，顶端源头）、L2=1–2、L3=3–5、L4=6–9、L5=10–14、L6=15–20、能源层=21–26。
- R1.3 邻接：三角网格（左/右儿子、左/右兄弟、左/右父），能源格仅与正上方 L6 格邻接（21↔15 … 26↔20）。
- R1.4 普通操作只作用于 id 0–20（`MAX_PLAYABLE_CELL_ID = 20`）。
- 实现：`board.py`（`_layer_index_to_id` / `_get_layer_and_index` / `_compute_neighbors` / `build_cells`）、`game.py:10`。

### R2 时间规则
- R2.1 默认限时 **25 分钟**（`TIME_LIMIT_MINUTES = 25.0`）；可用 `POST /api/time_limit` 修改（须为正数）。
- R2.2 计时从开局开始，`GET /api/tick` 为心跳接口（含超时判定）；超时即触发结算。
- 实现：`game.py:9,58-72`；`routes.py`（`/api/time_limit`、`/api/tick`）。

### R3 占领规则
- R3.1 占领入口：`cell_id` 须在 0–20，`team` 仅 `defender` / `attacker`。
- R3.2 **占领不可变**：除 L1 外，已占格不可覆盖、不可改变归属（含同阵营重复占领，直接忽略）。
- R3.3 占领后 `activated=False`，随后触发更新链（R9）。
- R3.4 清除占领（`cancel_occupy`）：owner→None 并触发更新链；清除 L1 时其 `l1_high_*` 纪录一并重置。
- 实现：`game.py:94-127`（occupy）、`game.py:165-186`（cancel_occupy）。

### R4 L1 源头特殊规则（能量引擎）
- R4.1 L1 **可随时被任何一方挑战、反复争夺**：提交 `score`（必填）+ `tp`（可选），**优先比 score，同分比 tp**，更高者易主；score、tp 均相同则持有方不变（先到先得）。
- R4.2 **得分豁免激活**：攻击方占领 L1 即得分，无需激活。
- R4.3 **能量积累**：攻击方占领 L1 **立刻 +1 能量**（含夺回）；攻击方持有期间**每 2 分钟 +1**；防守方夺回后**能量保留、暂停积累**；攻击方再夺回从保留值继续。
- R4.4 **L1 能量胜利**：能量满 **7 点** → 攻击方直接获胜（`win_type="l1_energy"`，防守方分数保留）。
- R4.5 **包围开关**：攻击方持有 L1 期间**包围机制整体失效**；防守方夺回后恢复。
- R4.6 **旧顶端直胜已移除**：攻击方占 L1 且激活不再秒胜（L1 激活不再影响胜负）。
- 实现：`game.py:78-101`（`_accrue_l1_energy` / `_l1_victory`）、`game.py:166-205`（`_occupy_l1`）、`game.py:288`（包围失效）。

### R5 激活规则
- R5.1 攻击方的格子**激活** ⟺ 存在一条从该格到某能源格的路径，路径上所有中间格均为攻击方占领。
- R5.2 激活状态在每次占领变化后**整体重算**（从 6 个能源格出发 BFS）。
- R5.3 未激活的攻击方格**不计分、不享能源加成**；连通路径被破坏（取消关键格 / 包围转换路径格）后立即变为未激活。
- R5.4 L1 若被攻击方占领且连通能源，也会被标记激活（**激活不再影响胜负**，仅保留标记）。
- 实现：`game.py:217-238`（`update_activation`）。

### R6 包围规则（新包围系统）
- R6.1 **区域构成**：连通区域 = 相邻的「未占领 + 攻击方未激活」格；**能源格（21–26）不参与**；**攻击方激活地块不属于区域**（与区域相邻则阻断包围）；**L1 可属于区域**。
- R6.2 **封闭判定**：区域内每格的每个邻接格，要么属于本区域，要么是**防守方占领**；邻接槽位缺失（=地图边界）视为封闭边。**邻接攻击方激活地块 / 能源格 → 不成立**；攻击方未激活地块不阻断（并入区域，成立时一并转换）。
- R6.3 **触发效果**：整片区域变为防守方地块（owner→"defender"、activated=False），分数由更新链即时重算；攻击方未激活地块被「吃掉」。
- R6.4 **触发时机**：每次占领 / 清除 / L1 挑战成功后随更新链判定，**可多次触发**；单次判定内迭代到不动点（纯 L1 区域无可转换格时跳过）。
- R6.5 **L1 豁免转换**：L1 可属于区域但包围成立时不被转换（不变成防守方地块）。
- 实现：`game.py:241-308`（`check_encirclement`）、`game.py:310-328`（`_region_enclosed`）。

### R7 计分规则
- R7.1 防守方：占领即得分（`total_score = 难度分 + 任务加分`），无需激活。
- R7.2 攻击方：L1（id 0）占领即得分；其余格**须激活**才计分。
- R7.3 能源加成（攻击方专属）：每个**已激活**格按所在连通块查 **`config/rules.json` 的 `energy_bonus_by_contact` 表**（键=接触能源数，超档封顶；缺表回退 `min(接触数−1, 2)`）：接触 1/2/3/≥4 个能源 → +0/+1/+2/+2。
- R7.4 连通块 = 通过邻接边互连的已激活攻击方格；接触能源数 = 块内任意格邻接的**不同**能源格数量；不同连通块各自独立计算。
- 实现：`game.py:331-364`（`recalc_scores`）、`game.py:366-383`（`_energy_bonus_for`）、`game.py:385-408`（`_bfs_attacker_block` / `_count_energy_contacts`）。

### R8 胜利规则
- R8.1 **L1 能量胜利**：攻击方持有 L1 期间能量满 7 点 → 立即获胜（`win_type="l1_energy"`），防守方当前分数**保留不变**（不吞噬、不累加）。
- R8.2 **计时结束**：限时到（或手动 `POST /api/end`）→ 比分高者胜，同分则平局（`draw`）。
- R8.3 所有格子被占满**不自动结算**，等待计时或手动 end。
- 实现：`game.py:78-101`（能量积累/胜利）、`game.py:240-259`（`end_game`）。

### R9 更新链（跨域约束，顺序不可变）
- R9.1 任何占领 / 清除 / L1 挑战成功后，固定执行：
  `update_activation` → `check_encirclement` → `recalc_scores` → `check_top_victory` →（未结束则 `_check_timeout`）。
- R9.2 **顺序不可颠倒**：激活决定包围判定（必须最先），包围决定分数重算，L1 能量检查在分数之后。
- 实现：`game.py:209-215`（`_run_update_chain`）。

## 第二部分 · 生成期规则（歌曲 / 难度 / 任务）

### R10 歌曲与难度
- R10.1 `level → diff_score` 只取**等级数值**，`type` 前缀（Glitch/Chaos/Hard）不影响；映射（`level_to_score`）：
  `15+/16/16+…≥16`→15、`15`→10、`14/14+`→8、`13/13+`→6、`12/12+`→5、`11/11+`→4、`9/9+/10/10+`→3、`≤8`→2。
- R10.2 歌曲库校验（`parse_song_library`）：`type` ∈ {Glitch, Chaos, Hard}、歌名非空且**唯一**、level 可解析；错误消息**带下标 + 中文原因**。
- R10.3 **开局硬约束：歌曲库 ≥23 首**，否则 `POST /api/init` 返回 400。
- 实现：`song_lib.py:25-55`（`level_to_score`）、`song_lib.py:58-91`（`parse_song_library`）、`song_lib.py:122-123`。

### R12 任务生成流水线（歌曲库模式，23→21）
- R12.1 随机抽 **23 首不重复** → 每首按任务表权重配任务 → 按 `diff_score + task_bonus` 降序 → **删最高 1 个 + 删最低 1 个** → 剩 21 恰好填满。
- R12.2 模板：每局等概率抽 A/B/C，按区域权重贪心落位。
- R12.3 区域（容量固定）：`top={0}`(1)、`mid={1..9}`(9)、`shallow={10..14}`(5)、`energy={15..20}`(6)。**注意：`energy` 指 L6 层（id 15–20），不是能源格（21–26）。**
- R12.4 贪心算法：权重 `high=3, medium=2, low=1`；区域按 `(权重降序, 固定顺序 energy→mid→shallow→top)` 排序；任务按得分降序逐一出队，放入「剩余空位>0 且排序最靠前」区域的随机空格，直至 21 个全部分配。
- R12.5 L1（id 0）固定 `task_bonus=10`、`task_name="L1源头 (固定+10)"`（song 字段保留其分配到的歌曲）。
- R12.6 同 seed 结果可复现（所有随机操作走局部 `random.Random(seed)`，不污染全局状态）。
- 实现：`song_lib.py:118-184`（`generate_tasks_from_songs`）、`song_lib.py:108-115`（区域与权重）。

- R14.2 仅用于无歌曲库场景的兼容验证；**正式开局必须走歌曲库流水线**。

### R15 规则数据源
- R15.1 外部数据：`config/rules.json`（难度映射 `difficulty_score`、16 项任务表 `tasks`、3 模板 `templates`、**测试歌曲难度权重池 `song_level_weights`**、**能源加成表 `energy_bonus_by_contact`**）。
- R15.2 **`difficulty_score` 仅为存档参考**，实际判定走 `level_to_score` 区间逻辑（两者键集不一致，勿直接读配置）。
- R15.3 `load_rules()` 在文件缺失 / JSON 损坏 / 缺键时**回退内置默认**并打 warning，不崩溃；文件键覆盖默认、缺失键由默认补齐；`RULES` 模块级缓存。
- R15.4 `rules.py` 内置默认与 `rules.json` 内容**需保持一致**（两处都有完整副本，`tests/test_rules.py` 有同步断言）。
- R15.5 `song_level_weights` 由 `tools/gen_test_songs.py` 消费（测试歌曲难度分布可配置）；`energy_bonus_by_contact` 由 `game.py` 消费（能源加成可配置）。
- 实现：`rules.py:48-80`（`load_rules`）。

### R17 成绩上传协议 v1（自动化通道）
- R17.1 鉴权：`X-Match-Token`（双方共用）+ `X-Team-Token`（`defender`/`attacker` 之一，与请求体 `team` 必须一致）；令牌仅开局后有效，常量时间比较。
- R17.2 可选签名：携带 `x-timestamp` + `x-signature` 即开启 HMAC-SHA256 校验（key=MATCH_TOKEN，canonical 含 method/path/timestamp/client_msg_id/原始 body）；时间差 >300 秒 → `STALE_REQUEST`；缺一 → `MISSING_AUTH`；不携带则跳过。
- R17.3 幂等：同一 `client_msg_id` 重复提交返回首次结果；`GET /api/v1/results/{client_msg_id}` 可复核。
- R17.4 短时间去重：同一 `(team, song, player)` 60 秒内重复上报 → `409 DUPLICATE_RESULT`。
- R17.5 限流：按 `(team, player)` 60 秒窗口最多 5 次、两次最小间隔 3 秒；超限 → `429 RATE_LIMITED` + `Retry-After`。
- R17.6 歌曲映射：不在歌曲库 → `404 SONG_NOT_FOUND`；在库但不在本局 21 格 → `404 SONG_NOT_IN_TASKS`；未开局 → `409 MATCH_NOT_STARTED`；已结束 → `409 MATCH_ENDED`。
- R17.7 **严格任务校验（默认开，`STRICT_TASK_CHECK=1`）**：MM 须 `mm=true`、FC 须 `full_combo=true`、tp 任务须 `tp>=X`、分数任务须 `score>=X*10000`、判定统计任务三项必填且不超限；**缺失关键字段同样视为不满足** → `422 TASK_NOT_SATISFIED`（附差距说明）；`STRICT_TASK_CHECK=0` 关闭。
- R17.8 占领结果：`occupied`（占领成功）/ `already_occupied`（已占忽略）/ `l1_holder`（L1 挑战成功）/ `l1_challenged_lost`（L1 未超过当前持有方）。
- R17.9 批量：`POST /api/v1/results/batch` 最多 **50 条**，逐条独立处理，单条失败不影响其他。
- 实现：`routes.py:335-647`；协议细节见 `成绩上传协议.md`。

### R18 事件日志格式
- R18.1 统一格式：`[mm:ss] <队伍> 占领了L<层>第<N>个格子 的<歌名> <任务> (<得分>) [标注]`（N 从 1 开始；歌名缺省回退难度标签；L1 含 `(score=…, tp=…)`）。
- R18.2 标注（可叠加）：`[防守]`（防守方）/ `[已激活]` / `[未激活]` / `[能源+N]`（连通块接触 ≥2 能源）/ `[占领L1]`（替代其他）。**旧 `[守卫]`、`[包围]` 标注已移除**。
- R18.3 特殊事件（初始化/包围成立/游戏结束）保持原文，时间为真实游玩时间；包围成立事件形如 `包围成立！N格变为防守方地块`。
- 实现：`game.py:377-389`（`_occupation_annotations` 等）。

## 第四部分 · 展示层与基础设施

### R19 前端约定
- R19.1 颜色：防守方=蓝（`--defender`）、攻击方=红（`--attacker`）；已激活格=左上角金色方块 + 右上角 `(+x)` 加成；未激活格半透明淡化（opacity 0.5）；能源格=暗金底金框。**旧包围的虚线边框 / 蓝点 / 包围状态面板已移除**。

### R20 基础设施
