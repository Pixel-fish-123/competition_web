# 三角占领 · 成绩上传协议 v1

玩家设备 / 机器人插件通过 HTTP 把单曲成绩上传给赛时控制器，控制器自动完成
「歌曲 → 任务格」映射、普通格占领与 L1 挑战。协议路径固定在 `/api/v1/*`，
控制器同时保留 `/api/occupy` 等人工操作接口（本协议是它们的自动化通道）。

## 1. 端点总览

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/results` | 上传单条成绩 |
| POST | `/api/v1/results/batch` | 批量上传（最多 50 条） |
| GET  | `/api/v1/tasks` | 当前 21 个任务格（含 L1） |
| GET  | `/api/v1/results/{client_msg_id}` | 查询某次上传的处理结果 |
| POST | `/api/init` | 开局：生成/返回比赛令牌与阵营令牌（协议前置） |

## 2. 令牌与鉴权

开局（`POST /api/init`）时会生成一组令牌，并在响应里返回：

```json
{
  "ok": true,
  "tokens": {
    "match": "<32位hex>",
    "defender": "<16位hex>",
    "attacker": "<16位hex>"
  }
}
```

- `X-Match-Token`：比赛令牌，双方共用，所有 `/api/v1/*` 请求必填；
- `X-Team-Token`：阵营令牌，取 `tokens.defender` / `tokens.attacker` 之一，
  请求体里的 `team` 必须与令牌阵营一致。

令牌也可在启动控制器前用环境变量 `MATCH_TOKEN` / `DEFENDER_TEAM_TOKEN` /
`ATTACKER_TEAM_TOKEN` 固定。每次 `POST /api/init` 都会重新生成（或重新读取
环境变量）并清空旧的幂等缓存，令牌**只在开局后有效**：

| 错误码 | HTTP | 含义 |
|--------|------|------|
| `MISSING_AUTH` | 401 | 缺少 `X-Match-Token` 或 `X-Team-Token` |
| `INVALID_TOKEN` | 401 | 令牌不匹配 |
| `TEAM_TOKEN_MISMATCH` | 403 | `team` 与 `X-Team-Token` 阵营不一致 |
| `MATCH_NOT_STARTED` | 409 | 尚未开局（未 `POST /api/init`） |

令牌校验用常量时间比较，避免时序侧信道。

### 可选签名（防篡改）

携带 `x-timestamp` + `x-signature` 两个请求头时开启 HMAC-SHA256 校验，缺一即
返回 `MISSING_AUTH`；不携带则跳过校验（适合内网机台）。签名算法：

```text
canonical = "POST\n" + path + "\n" + timestamp + "\n" + client_msg_id + "\n" + 原始请求体
signature = hex(hmac_sha256(key=MATCH_TOKEN, message=canonical))
```

`timestamp` 为 Unix 秒；与服务器时间差超过 300 秒返回 `STALE_REQUEST`。
批量接口的 `path` 为 `/api/v1/results/batch`，`client_msg_id` 用信封上的
（批量请求自身可带一个信封级 `client_msg_id`）。

## 3. 单条上传

`POST /api/v1/results`

```json
{
  "api_version": "1",
  "client_msg_id": "match3-defender-003",
  "team": "defender",
  "player": { "id": "qq:10001", "name": "阿晴" },
  "song": { "name": "Vindication", "level": "15+", "type": "Glitch" },
  "result": {
    "score": 9914200,
    "tp": 99.5,
    "mm": true,
    "full_combo": true,
    "miss": 0,
    "bad": 0,
    "good": 1
  },
  "client_ts": "2026-08-09T12:00:00+08:00",
  "device": { "id": "cabinet-03", "app": "arcaea" }
}
```

字段约束：

| 字段 | 必填 | 约束 |
|------|------|------|
| `client_msg_id` | 是 | 1-64 字符，幂等键，调用方自行保证唯一 |
| `team` | 是 | 仅 `defender` / `attacker` |
| `player.id` | 是 | 1-64 字符；机器人场景建议用 `qq:<QQ号>` |
| `player.name` | 否 | 字符串，展示用 |
| `song.name` | 是 | 需在歌曲库中（大小写敏感按字面匹配） |
| `song.level` / `song.type` | 否 | 字符串，仅回显 |
| `result.score` | 否* | 0-10000000 整数（L1 与 `w以上` 任务必填） |
| `result.tp` | 否 | 0-100 数字（`tp以上` 任务必填） |
| `result.mm` | 否 | 布尔（`MM` 任务必填） |
| `result.full_combo` | 否 | 布尔（`FULL COMBO` 任务必填） |
| `result.miss/bad/good` | 否 | 非负整数（`miss<=…` 任务必填） |
| `client_ts` / `device` | 否 | 字符串 / 对象，仅存档展示 |

结构错误统一返回 `400 VALIDATION_ERROR` + `message` 说明。

## 4. 处理规则

### 4.1 幂等（client_msg_id）

同一 `client_msg_id` 重复提交，直接返回首次处理的结果（状态码与响应体均一致），
不受限流影响。查询接口 `GET /api/v1/results/{client_msg_id}` 可随时复核。

### 4.2 短时间去重

同一 `(team, song, player)` 在 60 秒内重复上报（换一个 `client_msg_id`）返回
`409 DUPLICATE_RESULT`，防止机台抖动 / 客户端重试把同一首歌刷两遍。

### 4.3 限流

按 `(team, player)` 限流：60 秒滑动窗口最多 5 次、两次最小间隔 3 秒。超限返回
`429 RATE_LIMITED` + `Retry-After` 秒数。

### 4.4 歌曲与任务格

- 歌曲不在歌曲库 → `404 SONG_NOT_FOUND`；
- 在歌曲库但不在本局 21 格任务表 → `404 SONG_NOT_IN_TASKS`；
- 比赛未开局 → `409 MATCH_NOT_STARTED`；已结束 → `409 MATCH_ENDED`。

### 4.5 严格任务校验（默认开启）

`STRICT_TASK_CHECK=1`（默认）时，上传成绩必须满足格子任务要求，**缺失关键字段
同样视为不满足**（例如 MM 任务不传 `mm` 会返回 422 而不是放行）：

| 任务 | 判定 |
|------|------|
| 达成 MM | `result.mm` 必须为 `true` |
| 达成 FULL COMBO | `result.full_combo` 必须为 `true` |
| 达成 tp X 以上 | `result.tp` 必填且 `tp >= X` |
| 达成 X w 以上 | `result.score` 必填且 `score >= X*10000` |
| 达成 miss <= m, bad <= b, good <= g | 三项必填且均不超过限制 |

不满足返回 `422 TASK_NOT_SATISFIED`，`message` 里附具体差距（如
`成绩不满足任务要求（tp=98.5 < 99.5）：达成tp99.5以上`）。设置环境变量
`STRICT_TASK_CHECK=0` 可关闭该校验。

### 4.6 占领结果

处理成功返回 `200`，`outcome` 取值：

| outcome | 含义 |
|---------|------|
| `occupied` | 普通格占领成功 |
| `already_occupied` | 该格已被占领（占领不可变，不计分） |
| `l1_holder` | L1 挑战成功（score 更高，或同分 tp 更高） |
| `l1_challenged_lost` | L1 挑战未超过当前持有方 |

普通格 L1 之外的占领不可覆盖；L1 可反复争夺（先比 score，同分比 tp）。

## 5. 批量上传

`POST /api/v1/results/batch`，请求体为 `{ "client_msg_id": "批次标识（可选）", "items": [ … ] }`，
`items` 每条结构同单条上传，最多 50 条。逐条独立处理，单条失败不影响其他条目：

```json
{
  "ok": true,
  "items": [
    { "index": 0, "ok": true, "code": "RESULT_PROCESSED", "outcome": "occupied", "data": { … } },
    { "index": 1, "ok": false, "code": "TASK_NOT_SATISFIED", "message": "成绩不满足任务要求（…）" }
  ]
}
```

## 6. 示例

```bash
# 开局拿令牌
curl.exe -X POST http://127.0.0.1:8001/api/init -H "Content-Type: application/json" -d '{"mode":"random"}'

# 上传成绩
curl.exe -X POST http://127.0.0.1:8001/api/v1/results \
  -H "Content-Type: application/json" \
  -H "X-Match-Token: <match>" \
  -H "X-Team-Token: <defender>" \
  -d '{"api_version":"1","client_msg_id":"demo-001","team":"defender","player":{"id":"qq:10001"},"song":{"name":"Vindication"},"result":{"score":9914200,"tp":99.5,"mm":true}}'

# 查任务表
curl.exe http://127.0.0.1:8001/api/v1/tasks \
  -H "X-Match-Token: <match>" -H "X-Team-Token: <defender>"
```

## 7. 状态通道（WebSocket）

控制器同时提供 `GET /ws`（WebSocket）实时状态通道，机器人插件等客户端连上后：

- 连接建立后立即收到一帧 `{"type":"state_update", …}`（完整对局状态，字段同 `GET /api/state`）；
- 之后每次对局变更（开局、占领、L1、结束、改时限）都会推送同样的帧；
- **超时判定由控制器后台任务执行**（每 1s 检查一次），到点自动结束比赛并推送
  `game_over: true` 的状态帧，客户端无需再轮询 `/api/tick`（该接口仅保留兼容）。

客户端应处理断线重连：连接失败/断开后按指数退避（1s→2s→4s…，上限 30s）重连，
重连成功后以最新一帧状态为准（本地过期状态会被覆盖）。
